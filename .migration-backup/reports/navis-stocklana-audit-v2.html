Navis: Stocklana judge audit, round 2

Audit date: 20 September 2026 (IST). Auditor role: independent hackathon judge reading the public product and repository cold. Scope: the deployed site https://navis-gilt.vercel.app, GitHub main at a335681 (which Vercel production is built from), the local checkout (application code identical to a335681; only agent notes and attachments differ), the official Stocklana rules, and the two earlier reports (the first internal audit at 72/100 and the external report at 68/100).

Nothing in this audit changed deployment settings, secrets, databases, wallets or the submission. Evidence files written by this audit are listed in section 9.

1. Verdict

Navis is a well built, honest, simulation-first demonstrator of a governed equity agent: the model proposes, deterministic policy code decides, the wallet stays the authority, and every run produces a hash-verifiable receipt. Since the last audits the biggest judge complaint has been fixed: a judge can now press Run decision on the public site and get a fresh approved (Balanced) or rejected (Oversized) result with a verified receipt in about a second, on desktop and on a 375 px phone, with zero console errors.

What still holds it back is not code quality. It is that the product is still a demo of a pattern rather than a thing people would use tomorrow: nothing touches Solana on the public site, the tokenized-stock data (PreStocks) is displayed but never used by the agent, the fresh decision's own link is unreliable on Vercel, the first screen never explains what Navis is, and half the repository documentation still describes an older state of the project. A judge who reads the README first will be told the fixes they are looking at "are not yet pushed or deployed".

Score: 72/100. Confidence: medium-high. Same headline number as the first audit, but for different reasons: the demo score went up, the evidence and polish score went down because the documentation drifted while the code moved forward. This is an independent framework, not the official weighting.

3. Findings, ordered by judging impact

Severity is about points lost with a judge, not exploitability.

Must do before submission

F1. The fresh decision's own link is unreliable on the public site. Severity: High. Evidence: after running Balanced in production in a real browser, "Open decision detail" led to /decisions/9aba135a-... which rendered "Decision unavailable. Demo runs without a database are kept in memory for one server instance only." The same happened when reopening the smoke run's ID later. Fresh runs live in a process-global map of the last 50 runs, so the link works only when the follow-up request lands on the same warm serverless instance; the scripted smoke's immediate GET did succeed, the browser click did not. A judge who hits the failure will assume the flow is fake. Fix options, cheapest first: (a) hide the detail link when persisted.store === "memory" and render the full detail inline, which the panel already does; (b) make the detail page stateless by carrying the run in the URL as a compressed, HMAC-signed payload that the server verifies and re-renders. Note that simply attaching a database is not a fix: with DATABASE_URL set the run route requires a wallet session and returns 409 for persistent agents, and the service deliberately refuses a database for demo runs. Option (a) is under an hour; (b) is two to three hours.

F2. Repository documentation contradicts the live product. Severity: High for evidence and polish. A judge reads the README first. Evidence: README.md line 7 says local hardening "is not yet pushed or deployed"; line 119 to 121 quote 113 tests and commit ac26e54; docs/SUBMISSION_READINESS.md says "Public application URL: Missing", "Fresh proposal generation: Deferred", "Not ready to submit"; docs/DEMO_SCRIPT.md says fresh proposal generation "is deferred and must not be narrated"; docs/SUBMISSION_DRAFT.md line 17 says "Fresh proposal generation is deferred"; docs/EVIDENCE.md line 30 pins GitHub main at ac26e54; docs/SECURITY_REVIEW.md and docs/INTEGRATIONS.md still say the intent binding is "unresolved" in one paragraph and "implemented" in the next. The fix is a single documentation pass that rewrites each file to the state at a335681 and moves historical baselines into a clearly marked history section. About two hours. Also add a short "What changed" section to the README that links this report.

F3. No first-screen explanation of the product. Severity: High for "real user and problem". Evidence: / redirects to /agents/atlas; the first visible text is "Run new decision" and Atlas's mandate. Nothing says what Navis is, who it is for, or why Solana. A judge with 126 projects to review gives each one about two minutes. Fix: a compact intro card above the run panel or a real / landing with three lines (problem, what Navis does, what you can try right now) and two buttons (Run a decision, Verify a receipt). Half a day including copy.

F4. Submission package is incomplete. Severity: High for eligibility hygiene. Missing: LICENSE file (the rules require disclosure of open-source components; a licence is not strictly mandatory but every serious entry has one), pitch video, technical video, final track selection, team declaration. Evidence: no LICENSE* in the repository root; docs/SUBMISSION_DRAFT.md still has TODO video rows. Owner decisions, not code; one evening.

Should do if time allows

F5. PreStocks is displayed but never used by the agent. Severity: Medium for the main track, High for the PreStocks bounty. Evidence: the PreStocks catalogue is a read-only table on /markets/launch; the Atlas universe, portfolio and market inputs come from fixtures/demo-agent and the decision code never reads PreStocks data. The sponsor text is "build your project using PreStocks". Fix: let the demo universe be built from live PreStocks contract addresses (already validated by the adapter), and feed the PreStocks price and valuation into the policy facts for freshness and concentration checks, clearly labelled as research data and not execution quotes. Roughly one day; it also makes the run panel feel live because the numbers change.

F6. Nothing on the public site touches Solana. Severity: Medium for Solana fit. Evidence: health shows RPC not configured; receipts are offchain only; the demo would be identical on any chain. Two safe, cheap options that do not move funds: (a) configure a public devnet RPC in production and show a live read (current slot, the demo owner's devnet balance, or the DBC program account) on the Atlas page and in the receipt; (b) show a live read of the Meteora DBC program account and the PreStocks token mints from devnet or mainnet RPC in the markets page, proving the addresses Navis validates exist on chain. Option (a) is two hours plus one env var; (b) is half a day. Do not try to anchor demo receipts on chain this week: the receipt schema anchors the decision hash to the execution transaction signature and explicitly forbids demo receipts from claiming anchoring, so that would need a schema and service redesign.

F7. Decision detail returns 200 for unknown IDs. Severity: Low. Evidence: /decisions/does-not-exist renders the "unavailable" page with HTTP 200. Return 404 so crawlers and judges' tools see the truth. Fifteen minutes.

F8. Initial paint shows skeleton panels while the accessibility tree is already complete. Severity: Low. Evidence: tester's first desktop screenshot showed loading placeholders that resolved after interaction. Likely a client hydration gap on the run panel. One hour to inspect.

F9. Dependency advisories unchanged. Severity: Low to Medium. 6 high, 13 moderate, all transitive through the Solana and Meteora chains with no non-forced fix. Do not force upgrades before the deadline; instead add one paragraph to the security review with the reachability argument (bigint-buffer and toml are not on any request path the public demo executes). Thirty minutes.

Nice to have

  • Add a "Verify this receipt" input on /proofs so a judge can paste a fresh receipt JSON and hash rather than only viewing the fixture receipt.
  • Persist fresh runs when a database is present (currently authenticated persistent-agent runs return 409 by design, unauthenticated ones 401). Keep the honest 409 until the facts problem is solved.
  • Pin latest dependencies in package.json to the versions in the lockfile so a fork with npm install gets the tested build.
  • Replace the second-person "Return to Atlas" dead-end with a "Run again" button that carries the scenario.
  • Record a 90-second silent screen capture of the Balanced and Oversized runs and embed it in the README; judges who cannot load the site still see it working.
